# A/B Verdict: финальный spec MVP

*Команда 10 · 7 ноября 2026 · Максим, по итогам ревью дизайна Дмитрия (`feature/verdict-agent`) и заметок `research/06-ab-guard-mvp.md`. Демо: воскресенье 8 ноября, 15:00.*

Этот документ сводит две проработки одной идеи в один план. Он не заменяет OpenSpec Дмитрия (`openspec/changes/add-verdict-agent/`), а дополняет его: решает открытые расхождения, добавляет UI и описывает, кто что делает. После согласования правки уходят в OpenSpec и в план реализации.

## 1. Одной фразой

Adapty раздаёт варианты и считает деньги, а решение «останавливать ли тест» человек и AI-агент принимают по сырому P2BB, который считает только полученную выручку. Мы встраиваем в этот момент вердикт: можно ли уже верить лидеру с учётом висящих триалов и будущих продлений, сколько стоит ошибка и что делать дальше. Это функция, которую Adapty может встроить в страницу A/B-теста.

## 2. Проблема и для кого

**Для кого.** Growth-менеджер подписочного приложения и AI-агент, которым он ведёт тесты.

**Что сейчас.** Менеджер видит «B 100%» и либо останавливает рано, либо ждёт «недели две» без даты. Агент со скиллом `ab-tests` останавливает по сырому P2BB: Predicted P2BB есть только в дашборде, в CLI и MCP есть лишь `probability`.

**Почему это не лечится трафиком.** Вариант, который получает деньги сразу (годовой, lifetime), со временем всё сильнее «обгоняет» вариант с продлениями, потому что не пришедшие продления никто не считает. Ошибка растёт с данными.

**Цифры.** Офлайн-данные Lumen, тест Settings, 100 пользователей в день на вариант, 14-й день:

| | Сырой P2BB | Вердикт по ожидаемой выручке |
|---|---|---|
| Неверный уверенный лидер | 17% прогонов | 5% |
| Верное уверенное решение | 22% | 43% |

На 60 днях побеждает `main_lifetime`: $12,60 против $10,80 на пользователя. В `06` приведена другая ячейка того же eval (28-й день: 29% против 1%). На слайд берём одну пару после прогона `eval/verdict_eval.py` (задача 9.1 у Дмитрия); до этого в документах используем пару 14-го дня, потому что демо показывает 14-й день.

## 3. Решения по открытым вопросам

| Вопрос | Решение | Почему |
|---|---|---|
| Guardrails блокируют вердикт или предупреждают | **Предупреждают.** Добавляют альтернативный тест в `next_step.alternative` | В Onboarding рефандов на пользователя 2,4× больше у weekly, а на платящего 1,2×, и рефанды уже вычтены из выручки. Блокировка здесь была бы ошибкой |
| SRM и «мёртвая рука» | **В MVP**, блок `checks` | Час работы, живой кадр на Onboarding (285 против 254, χ² ≈ 1,8, p ≈ 0,18). Сломанный тест помечаем `broken`, вердикт при этом не выносим |
| Реальный `ab-tests stop` после «да» человека | **Не делаем.** Инструмент только читает | Необратимо, общий аккаунт, и read-only это чистый ответ на вопрос о рисках. Вместо действия показываем карточку «что увидят пользователи после остановки» |
| Модель ожидаемой выручки | **Калибровочная таблица по продукту** из истории, нормальная аппроксимация разницы средних (как у Дмитрия) | Проверена eval'ом. В живом Lumen завершённых триалов 0, обновлять априор по руке нечем. Обновление априора закрывшимися триалами руки записываем как следующий шаг и готовим ответ жюри |
| Досев в Lumen | **Разрешён**, правило про `seed_adapty.py` было нашим | См. раздел 6 |
| Герой демо | **UI-сюжет.** Человек открывает страницу теста и видит вердикт. MCP показываем вторым кадром | Визуально сильнее, чем JSON в терминале |

## 4. Что строим: три поверхности над одним ядром

```
                 ┌──────────────────────────────────────┐
                 │  verdict_agent (Python, stdlib core)  │
                 │  estimator · stats · verdict · checks │
                 │  guardrails · segments · calibration  │
                 └───────────────┬──────────────────────┘
          offline.py (CSV) ──────┤────── live.py (Adapty CLI, read-only)
                                 │
                        service.verdict() → один JSON
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
          python -m        MCP stdio         HTTP (FastAPI)
          verdict_agent.cli  ab_test_verdict   GET /api/...
                 │               │               │
              терминал      Claude / агент    Web UI (React + Vite)
                            + SKILL.md       «страница A/B-теста»
```

Правила:

- **Вся логика в ядре.** UI, CLI и MCP только показывают JSON. Иначе eval не покрывает то, что видит жюри.
- **Один JSON-контракт** (`schema.json`), один и тот же во всех трёх поверхностях. Тест на равенство CLI и MCP уже в плане Дмитрия; добавляем HTTP.
- **LLM внутри нет.** Текст пишет вызывающий агент из чисел JSON. UI текста не генерирует, только шаблоны.
- **Adapty только читаем.** Единственная запись в Adapty это досев данных до демо, отдельным скриптом, не из продукта.

## 6. Данные: что живое, что досеяно, что офлайн

| Тест | Источник | Что покажет | Бейдж в UI |
|---|---|---|---|
| Onboarding: annual trial vs weekly first | живой Lumen | B впереди, 137 триалов в полёте, A с $0. Ожидаем `early` или `confirmed`, конкретный исход не обещаем. SRM в норме | `Live` |
| Main: 3 plans vs lifetime anchor | живой Lumen | 2 покупки на 77 пользователей → `not_enough_data` с датой. Показывает, что «66,84%» в Adapty ничего не значит | `Live` |
| Settings-подобный тест, новый | досев в Lumen | 14-й день: сырой P2BB уверен в одной руке, вердикт `early` с датой и суммой | `Live · seeded` |
| Settings, Main, Onboarding из офлайн-датасета | CSV, 50 000 пользователей, 120 дней | Сегменты, зрелость по неделям, eval | `Offline dataset` |

**Досев: план и запасной путь.** Цель досева: чтобы тест типа Settings жил в Lumen и UI читал его тем же живым путём, что Onboarding. Схема: создать и запустить новый flow-тест на плейсменте `settings_upgrade` (старый Settings завершён и перезапуску не подлежит), затем `setTransaction` с `variation_id` рук и датами покупок за прошлые 14 дней по историческим ставкам с разбросом, без подгонки под вердикт.

Два факта не проверены, и от них зависит всё:

1. Считает ли тест транзакции с `purchased_at` раньше его старта. Если нет, все покупки лягут в один день, и зрелости не будет.
2. Поле `users` в метриках теста равно `views`. `setTransaction` просмотров не создаёт. Проба через Web API `paywall/visit/` дала `variation_id`, которого нет среди рук, и `users` не изменился. Без `users` выручка на пользователя не считается.

Правило: **на досев два часа с момента старта, проверка пунктов 1 и 2 в первый час.** Если любой не подтверждается, Settings показываем из офлайн-датасета с бейджем `Offline dataset` тем же экраном. Демо-сценарий написан так, что работает в обоих случаях.

Калибровка: живой `analytics conversion` по продуктам сначала пробуем; если не отвечает, таблица из офлайн-датасета и поле `calibration_source: "offline"` в JSON и в UI.

## 7. UI: страница A/B-теста в стиле Adapty

### Стек и дизайн-система, снятые с app.adapty.io

- **Стек дашборда Adapty:** React SPA, сборка Vite (хэшированные чанки, CSS Modules вида `_Name_hash`), TanStack Query, zustand, Sentry. Берём то же: React + TypeScript + Vite, CSS Modules, без UI-библиотеки. Данные через `fetch` к нашему HTTP API.
- **Шрифты:** Inter для текста (14px/20px, вес 400; подписи 12px), Inter Tight для заголовков (`--a-text-title`: 20px/28px, вес 600; `display-1`: 24px/32px). Подключаем Inter и Inter Tight с Google Fonts.
- **Цвета (CSS-переменные Adapty, копируем в `tokens.css`):**
  - текст `--blackPrimary: #111`, вторичный `--black-600: #696969`;
  - primary `--purplePrimary: #6720ff`, hover `#7e41ff`, мягкий фон `--softBackground: #f8f4ff`, нейтральный `#faf9fc`;
  - рамки `--borderColor: #e7e7e7`, hover-фон `#f3f3f3`;
  - статусы: зелёный `--green-400: #1ea672` и `--green-50: #f2faf5`; жёлтый `--yellow-400: #eeae40` и `--yellow-50: #faf7ed`; красный `--red-400: #d74247` и `--red-50: #fcedef`; синий `--blue-400: #4777ff`.
- **Геометрия:** сетка 4px (`--a-spacing-base`), скругление кнопок 8px, пунктов меню 6px, карточки с рамкой 1px `#e7e7e7` и скруглением 12px, контент шириной 960px, левый сайдбар 240px белый с внутренней рамкой 1px.
- **Паттерны со страницы теста:** хлебные крошки «← A/B tests / Имя теста», ряд иконок-действий (View in analytics, Duplicate, Modify, Stop), карточка статуса (Status · Live с зелёной точкой, Started at, Duration, Placement), таблица рук с чекбоксом цвета руки (B фиолетовый, A оранжевый) и пилюлей веса «50%», колонка P2BB, колонка Predicted P2BB с текстом «insufficient data».

## 9. Агентная поверхность

- **MCP-тул `ab_test_verdict`** (stdio, Python MCP SDK), параметры `ab_test_id` или `offline_test` + `day` + `traffic`, плюс необязательные пороги. Описание тула дословно: «Read-only verdict for an Adapty A/B test. Call it before stopping a test or choosing a winner. Returns JSON only. When you explain it, use only numbers that appear in the JSON, state the verdict as given in `verdict`, and say whether the data is live, seeded or offline.»
- **`SKILL.md`** в репозитории, в формате Adapty skills: когда вызывать (перед `ab_tests_stop`, при «кто побеждает», «можно останавливать»), как объяснять, чего не делать (не останавливать тест, если вердикт не `confirmed`, без явного подтверждения человека). Это показывает, как фича встраивается в экосистему `adapty-skills`.
- **Проверка текста агента** (eval 4 у Дмитрия): три записанных ответа Claude, каждое число есть в JSON, вердикт совпадает.

## 10. Eval

Без изменений относительно плана Дмитрия, плюс один пункт:

1. Вердикт против 60-дневной правды на днях 1, 3, 7, 14, 21, 28 при 30 и 100 пользователях в день, три теста, 150 повторов.
2. Сегменты-пустышки: 20 случайных × 20 прогонов, найдено ≤ 1.
3. Live = offline по среднему ожидаемой выручки на одних данных.
4. Текст агента на записанных ответах.
5. **Новое:** SRM на 1 000 честных разбиениях 50/50 даёт `broken` не чаще 1%.

Ограничение произносим вслух и пишем рядом с каждой цифрой: подвыборки берутся с повторением из ~900 пользователей Settings, это завышает уверенность.
