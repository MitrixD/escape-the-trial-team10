*Команда 10 · 7 ноября 2026 · Максим. Версия 3, сверена с PR #10 (план OpenSpec с параллельными треками). Демо: воскресенье 8 ноября, 15:00.*

- Досев данных в Lumen разрешён, если нужно показать аномалию.

## 1. Одной фразой

Adapty раздаёт варианты и считает деньги, а решение «останавливать ли тест» человек и AI-агент принимают по сырому P2BB, который считает только полученную выручку и поэтому перекошен в пользу вариантов, которые платят сразу. Мы встраиваем в этот момент вердикт: можно ли уже верить лидеру с учётом висящих триалов и будущих продлений, сколько стоит ошибка и что делать дальше. Это функция для страницы A/B-теста в Adapty.

## 2. Проблема, для кого, цифры

**Для кого.** Growth-менеджер подписочного приложения и AI-агент, которым он ведёт тесты.

**Что сейчас.** Менеджер видит «B 100%» и либо останавливает рано, либо ждёт «недели две» без даты. Агент со скиллом `ab-tests` останавливает по сырому P2BB: Predicted P2BB есть только в дашборде и появляется через ~2 недели, в CLI и MCP есть лишь `probability`.

**Честная формулировка** (из `eval/RESULTS.md`). При большой разнице между вариантами дашборд редко ошибается уверенно, и живой Onboarding тому пример. Опасный случай: вариант, который платит сразу, против варианта с триалом и продлениями. Там сырой P2BB перекошен в пользу первого, и перекос растёт с данными, трафик его не лечит. Вердикт убирает перекос и в очевидных тестах решает раньше, чем «подождать две недели».

**Цифры для слайда.** Офлайн-данные Lumen, 100 пользователей в день на вариант:

| Тест и срез | Сырой P2BB | Вердикт |
|---|---|---|
| Синтетический «annual upfront vs weekly trial», дни 3–60: сырой P2BB уверен в неверной руке | **100% прогонов** | неверных `confirmed` **0%**, верных 90% к 14-му дню |
| Settings, горизонт 60, день 14: верное уверенное решение | 22% | **43%** |
| Settings, горизонт 90, день 28: уверенно неверное решение | **29%** | **1%** |

Деньги: самые большие потери не от неверной остановки, а от лишнего ожидания. Решение «на 14-й день» в очевидном тесте стоит $5–6 тыс. за тест в масштабе Lumen и $50–65 тыс. при трафике ×10. Каждую цифру сопровождаем оговоркой: повторы берут пользователей с возвращением, доли `confirmed` это верхняя оценка; в синтетическом тесте калибровка идеальна по построению.

## 3. Решения по открытым вопросам

| Вопрос | Решение | Почему |
|---|---|---|
| Guardrails блокируют вердикт или предупреждают | **Предупреждают**, как в первой реализации | В Onboarding рефандов на пользователя 2,4× больше у weekly, на платящего 1,2×, и рефанды уже вычтены из выручки |
| Калибровка ожидаемой выручки | **По живым данным Adapty** по продуктам: `analytics conversion trial-paid`, `ltv`, `cohort`. Офлайн-таблица из датасета как запасной путь, источник виден в `calibration_source` | Так инструмент работает на любом приложении, а не только на Lumen. В первой реализации живой `conversion` вернул строки только по продуктам с триалами и с дублями ключей, поэтому запасной путь обязателен |
| Пороги | **Параметры** `service.verdict()`, CLI, MCP и HTTP, дефолты из design.md, значения возвращаются в JSON | Нужны ползункам UI и показывают, что пороги не магические |
| `tie` на недонаборе | **Делим**: `tie` только когда разница доказуемо меньше минимального обнаружимого эффекта, иначе новый вердикт `keep_running` с датой | На Settings день 14 `tie` в 57% повторов при правде за `main_lifetime`. Совет «сменить рычаг» на недоборе вводит в заблуждение |
| SRM и «мёртвая рука» | **В MVP**, в change `add-verdict-web`, как проверки поверх вердикта | Час работы, живой кадр на Onboarding (285 против 254, χ² ≈ 1,8, p ≈ 0,18) |
| Реальный `ab-tests stop` | **Не делаем.** Только чтение. Вместо действия карточка «что увидят пользователи после остановки» | Необратимо, общий аккаунт |
| Досев в Lumen | **Разрешён**, если нужно показать аномалию, которой нет в живых тестах | Живые тесты дают `confirmed` и `not_enough_data`; ловушка видна только на данных с отложенной выручкой |
| UI | **Отдельный change `add-verdict-web`, последний шаг.** Из Non-Goals `add-verdict-agent` строка про UI убирается | Не блокирует валидацию и архив основного change |
| `SKILL.md` | **Не делаем** | MCP-описания достаточно |
| Герой демо | **UI-сюжет**, MCP вторым кадром | Визуально сильнее JSON в терминале |

## 4. Что строим: три поверхности над одним ядром

```
                 ┌──────────────────────────────────────┐
                 │  verdict_agent (Python, stdlib core)  │
                 │  estimator · stats · verdict          │
                 │  guardrails · segments · calibration  │
                 └───────────────┬──────────────────────┘
          offline.py (CSV) ──────┤────── live.py (Adapty CLI, только чтение)
                                 │        + живая калибровка по продуктам
              service.verdict(ab_test_id | offline_test, day, traffic,
                              horizon, thresholds)
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
          CLI              MCP               HTTP (FastAPI)      ← add-verdict-web
          python -m        ab_test_verdict    GET /api/tests, /verdict
          verdict_agent.cli                   + checks + карточка эффекта
                 │               │               │
              терминал      Claude / агент    Web UI (React + Vite)
                                             «страница A/B-теста»
```

Правила, общие с CLAUDE.md из PR #10:

- **Вся математика вердикта в ядре.** UI, CLI и MCP показывают его JSON. HTTP-слой добавляет конверт с данными экрана и проверками теста, вердикт не пересчитывает.
- **JSON ядра один и тот же** во всех поверхностях, по `verdict_agent/schema.json`. HTTP отдаёт его в поле `verdict` без изменений.
- **LLM внутри нет.** Текст пишет вызывающий агент. UI текста не генерирует, только шаблоны из полей.
- **Adapty только читаем** через один `AdaptyCLI` с allowlist, пауза ≥ 0,5 с, `apps get` запрещён, на 429 стоп. HTTP-слой ходит в Adapty только через него.
- **Ошибки безопасны** на всех поверхностях: `{"error": …}` без traceback, без значений из `.env`, `whoami` и stderr Adapty. HTTP вызывает `safe_verdict`.
- **Процесс.** Ветка от `main` на задачу `feat/<номер>-<имя>`, один PR в `main`, заголовок на английском, описание на русском. Любое изменение поведения через `openspec-update-change`, тест первым.

Офлайн-датасет: `https://github.com/kpotehin/adapty-seed-data-hack`, папка `data/offline`, путь в `VERDICT_DATASET`.

**Калибровка.** В live-режиме сначала живая таблица по продуктам из истории приложения (2.3), при нехватке данных по продукту офлайн-таблица без пользователей одноимённого офлайн-теста. В JSON и UI виден источник. Для Lumen живая история есть с июля, но 95% её без привязки к плейсменту, поэтому калибруем по продукту, не по плейсменту.

**Досев.** Разрешён для показа аномалии, которой нет в живых тестах, в первую очередь для синтетического теста «annual upfront vs weekly trial», чтобы он читался тем же live-путём. Условия: отдельный скрипт вне `verdict_agent`, запуск по согласованию, после того как UI работает на фикстурах, таймбокс 2 часа. Два факта проверяются в первый час: считает ли тест транзакции с `purchased_at` раньше старта, и что `users` в метриках теста не остаётся нулём (`users = views`, `setTransaction` просмотров не создаёт). Live-режим считает возраст от старта теста, поэтому для досеянного теста с историей нужна правка `live.py` через OpenSpec. Если что-то не подтверждается, тест показываем офлайн с бейджем тем же экраном.

## 7. UI: страница A/B-теста в стиле Adapty

### Стек и дизайн-система, снятые с app.adapty.io

- **Стек дашборда Adapty:** React SPA, сборка Vite (хэшированные чанки, CSS Modules вида `_Name_hash`), TanStack Query, zustand, Sentry. Берём React + TypeScript + Vite, CSS Modules, без UI-библиотеки. Данные через `fetch` к нашему HTTP API.
- **Шрифты:** Inter для текста (14px/20px, вес 400; подписи 12px), Inter Tight для заголовков (20px/28px, вес 600; display 24px/32px). Подключаем с Google Fonts.
- **Цвета (CSS-переменные Adapty, копируем в `tokens.css`):** текст `#111`, вторичный `#696969`; primary `#6720ff`, hover `#7e41ff`, мягкий фон `#f8f4ff`, нейтральный `#faf9fc`; рамки `#e7e7e7`, hover-фон `#f3f3f3`; статусы: зелёный `#1ea672` на `#f2faf5`, жёлтый `#eeae40` на `#faf7ed`, красный `#d74247` на `#fcedef`, синий `#4777ff` на `#f2f7ff`.
- **Геометрия:** сетка 4px, скругление кнопок 8px, пунктов меню 6px, карточки с рамкой 1px и скруглением 12px, контент 960px, левый сайдбар 240px белый с внутренней рамкой.
- **Паттерны со страницы теста Adapty:** хлебные крошки «← A/B tests / Имя теста», ряд иконок-действий (View in analytics, Duplicate, Modify, Stop), карточка статуса (Status · Live с зелёной точкой, Started at, Duration, Placement), таблица рук с чекбоксом цвета руки (B фиолетовый, A оранжевый) и пилюлей веса «50%», колонки P2BB и Predicted P2BB с текстом «insufficient data».

```
[Thresholds ▾] P confirm 95% · maturity 80% · min events 30 · MDE 5% · lifetime 180 d
```

Поведение:

- Страница рендерит JSON ядра плюс конверт. Ползунок «As of day» (максимум = горизонт, потому что offline отклоняет `day > horizon`), «Traffic/day», «Horizon» (1–120) и панель «Thresholds» запрашивают `/verdict` с параметрами, ядро пересчитывает. Для живых тестов ползунка дня нет.
- Данные читаются из кэша на диске. «Refresh» делает один живой проход (~5 чтений плюс калибровка, 0,5 с между вызовами) и показывает время обновления. На демо кэш прогрет, «Refresh» нажимаем один раз на Onboarding.
- Кнопка «Stop» видна, но отключена, с подсказкой «Read-only prototype. Stop in Adapty after the verdict».
- Для живых тестов блок Segments показывает «Not available on live data», а не «0 checked».
- `keep_running` подписывается «Not provable yet, keep running until <date>», `tie` подписывается «No meaningful difference».
- Тексты шаблонные, на английском, из полей JSON. Никакой генерации. Ошибки API показываются как есть из `{"error": …}`.

## 8. Контракт данных

**JSON ядра** по `verdict_agent/schema.json` (`additionalProperties: false`). Поля из спеки: `ab_test_id`, `verdict`, `leader`, `p2bb_expected`, `p2bb_raw`, `horizon_days`, `horizon_source`, `maturity`, `come_back_on`, `money_at_stake_usd`, `arms[]` (`title`, `users`, `revenue_received`, `revenue_expected_trials`, `revenue_expected_renewals`, `warnings[]`), `segments_checked`, `segments_found[]`, `next_step`, `source`, `calibration_source`. Выручка в `arms[]` в USD на пользователя, `money_at_stake_usd` итог, продления могут быть отрицательными.

## 10. Eval

1. Сетка вердикта против 60-дневной правды: 3 теста × дни 1, 3, 7, 14, 21, 28 × 30 и 100 пользователей в день × 150 повторов (8.1).
2. Шумовые сегменты: 20 прогонов × 20 случайных атрибутов, найдено ≤ 1 (8.2).
3. Синтетический тест «annual upfront vs weekly trial»: сетка на 100 повторов при 100 и 300 в день, ожидаем `raw_wrong` 100% и `wrong_confirmed` 0% (8.3).
4. Текст агента на записанных ответах (9.1).
5. Ложные срабатывания SRM на 1 000 честных разбиениях 50/50, `broken` ≤ 1% (10.2).

Ограничения повторяем рядом с каждой цифрой: ресемплинг с возвращением из небольших популяций, идеальная калибровка в синтетическом тесте, горизонт не больше 120 дней.
