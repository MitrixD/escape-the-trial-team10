# A/B Verdict: финальный spec MVP

*Команда 10 · 7 ноября 2026 · Максим. Версия 2, сверена с реализацией Дмитрия в `feature/verdict-agent` (PR #9, ядро, CLI, MCP, eval, README и демо-скрипт готовы). Демо: воскресенье 8 ноября, 15:00.*

Этот документ сводит две проработки одной идеи в один план: дизайн Дмитрия и `research/06-ab-guard-mvp.md`. Он не заменяет OpenSpec в `openspec/changes/add-verdict-agent/`, а дополняет его UI-поверхностью, закрывает расхождения и описывает, что осталось сделать и кому.

**Что изменилось во второй версии после чтения ветки Дмитрия:**

- Ядро готово. Разделы «кто что делает» и «фичи» переписаны из плана в статус.
- Живой Onboarding даёт `confirmed` для B уже в день 0, и по офлайн-правде дашборд на этом тесте прав. История «дашборд ошибается» на Onboarding не рассказывается. Демо и макеты переписаны на реальные числа из фикстур.
- Settings на 14-й день даёт `tie`, а не `early`. Ползунок дня в UI показывает путь `early` (день 7) → `tie` (день 14) → `confirmed` (день 28).
- Цифры для слайда исправлены: 17% против 5% это «неверный лидер впереди», а не уверенное неверное решение. Уверенные ошибки сырого P2BB на горизонте 60 дней редки; на 90 днях к 28-му дню 29% против 1%.
- JSON-контракт ядра закрыт (`additionalProperties: false`). Поля для UI идут в конверт HTTP-ответа, ядро не трогаем.
- Пороги в ядре это константы, параметром сделан только горизонт (1–120 дней). Панель порогов в MVP сужена до горизонта.
- Досев в Lumen снят с основного пути: он конфликтует с допущением live-режима «все пользователи установили приложение в день старта теста» и с правилами из CLAUDE.md ветки Дмитрия. Settings показываем офлайн с бейджем.

## 1. Одной фразой

Adapty раздаёт варианты и считает деньги, а решение «останавливать ли тест» человек и AI-агент принимают по сырому P2BB, который считает только полученную выручку и поэтому перекошен в пользу вариантов, которые платят сразу. Мы встраиваем в этот момент вердикт: можно ли уже верить лидеру с учётом висящих триалов и будущих продлений, сколько стоит ошибка и что делать дальше. Это функция для страницы A/B-теста в Adapty.

## 2. Проблема, для кого, цифры

**Для кого.** Growth-менеджер подписочного приложения и AI-агент, которым он ведёт тесты.

**Что сейчас.** Менеджер видит «B 100%» и либо останавливает рано, либо ждёт «недели две» без даты. Агент со скиллом `ab-tests` останавливает по сырому P2BB: Predicted P2BB есть только в дашборде и появляется через ~2 недели, в CLI и MCP есть лишь `probability`.

**Честная формулировка питча** (из `eval/RESULTS.md`). При большой разнице между вариантами дашборд редко ошибается уверенно, и наш живой Onboarding тому пример. Опасный случай: маленькая разница и вариант с отложенной выручкой. Там сырой P2BB перекошен в пользу варианта, который платит сразу, и перекос растёт с данными, трафик его не лечит. Вердикт убирает перекос и в очевидных тестах решает раньше, чем «подождать две недели».

**Цифры для слайда**, офлайн-данные Lumen, тест Settings, 100 пользователей в день на вариант, 150 повторов на ячейку:

| Срез | Сырой P2BB | Вердикт |
|---|---|---|
| Горизонт 60 дней, день 14: верное уверенное решение | 22% | **43%** |
| Горизонт 60 дней, день 14: уверенно неверное решение | ~0% | **0%** |
| Горизонт 90 дней, день 28: уверенно неверное решение | **29%** | **1%** |

Деньги: самые большие потери не от неверной остановки, а от лишнего ожидания. Решение «на 14-й день» в очевидном тесте стоит $5–6 тыс. за тест в масштабе Lumen и $50–65 тыс. при трафике ×10. Вердикт останавливает, как только это безопасно, и остаётся безопасным в тонких тестах. Каждую цифру сопровождаем оговоркой: повторы берут пользователей с возвращением из ~900 на вариант, доли `confirmed` это верхняя оценка.

## 3. Решения по открытым вопросам

| Вопрос | Решение | Почему |
|---|---|---|
| Guardrails блокируют вердикт или предупреждают | **Предупреждают.** Так уже реализовано | В Onboarding рефандов на пользователя 2,4× больше у weekly, на платящего 1,2×, и рефанды уже вычтены из выручки |
| SRM и «мёртвая рука» | **В MVP**, но в конверте HTTP, не в ядре | Час работы, живой кадр на Onboarding (285 против 254, χ² ≈ 1,8, p ≈ 0,18). Не трогает схему и OpenSpec Дмитрия |
| Реальный `ab-tests stop` | **Не делаем.** Только чтение | Необратимо, общий аккаунт. Вместо действия карточка «что увидят пользователи после остановки» |
| Модель ожидаемой выручки | **Калибровочная таблица по продукту**, как реализовано | Проверена eval'ом. Обновление априора по руке закрывшимися триалами это следующий шаг и готовый ответ жюри |
| Досев Settings-подобного теста в Lumen | **Снят с основного пути**, см. раздел 6 | Live-режим считает возраст всех пользователей от старта теста; досеянные покупки с прошлыми датами сломают оценку. Плюс `users = views` не решено |
| Герой демо | **UI-сюжет**, MCP вторым кадром | Визуально сильнее, чем JSON в терминале. Тезисы и числа берём из `docs/demo-script.md` Дмитрия |
| `tie` на недонаборе | В UI подпись «No provable difference yet», не «Tie». Разделение `tie` на «ничья» и «добрать данные» это первое изменение ядра после демо, если Дмитрий не успеет до | Известное ограничение из README: на Settings день 14 `tie` в 57% повторов, хотя правда за `main_lifetime` |

## 4. Что строим: три поверхности над одним ядром

```
                 ┌──────────────────────────────────────┐
                 │  verdict_agent (Python, stdlib core)  │  ✔ готово
                 │  estimator · stats · verdict          │
                 │  guardrails · segments · calibration  │
                 └───────────────┬──────────────────────┘
          offline.py (CSV) ──────┤────── live.py (Adapty CLI, ~5 чтений)
                                 │
              service.verdict(ab_test_id | offline_test, day, traffic, horizon)
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
          CLI ✔            MCP ✔             HTTP (FastAPI)  ← делаем
          python -m        ab_test_verdict    GET /api/tests, /verdict
          verdict_agent.cli                   + checks + карточка эффекта
                 │               │               │
              терминал      Claude / агент    Web UI (React + Vite)  ← делаем
                            + SKILL.md ←      «страница A/B-теста»
```

Правила:

- **Вся математика вердикта в ядре.** UI, CLI и MCP показывают его JSON. HTTP-слой добавляет вокруг него конверт с данными для экрана и проверками теста, но сам вердикт не пересчитывает.
- **JSON ядра один и тот же** во всех трёх поверхностях, по `verdict_agent/schema.json`. HTTP отдаёт его в поле `verdict` без изменений.
- **LLM внутри нет.** Текст пишет вызывающий агент из чисел JSON. UI текста не генерирует, только шаблоны из полей.
- **Adapty только читаем.** Это правило уже закреплено в CLAUDE.md ветки Дмитрия.
- **Изменения ядра** идут по его правилам: ветка от `feature/verdict-agent`, PR туда, OpenSpec для любого изменения поведения, тест первым. UI и HTTP-слой живут в `web/` и этих правил не касаются, кроме ветки и PR.

Офлайн-датасет: `git clone https://github.com/kpotehin/adapty-seed-data-hack`, папка `data/offline`, путь в `VERDICT_DATASET`.

**Почему досев снят с основного пути.** Три факта из реализации:

1. Live-режим считает возраст всех пользователей как `сегодня − старт теста`, потому что в Lumen все пользователи тестов пришли 7 ноября. Досеянный тест с покупками за прошлые 14 дней получит неверные возрасты, а значит неверную ожидаемую выручку. Чинить это значит менять `live.py` и OpenSpec в ночь перед демо.
2. `users` в метриках теста равно `views`, `setTransaction` просмотров не создаёт, проба через Web API дала чужой `variation_id`. Без пользователей нет выручки на пользователя.
3. CLAUDE.md ветки Дмитрия запрещает запись в Adapty и повторный сид. Правило наше, но менять его ради рискованной ветки работы не стоит.

Если всё же делать: только после того, как UI на фикстурах работает, с таймбоксом 2 часа, и только если пункты 1 и 2 проверены за первый час. Запасной путь в любом случае тот же экран с бейджем `Offline dataset`.

## 7. UI: страница A/B-теста в стиле Adapty

### Стек и дизайн-система, снятые с app.adapty.io

- **Стек дашборда Adapty:** React SPA, сборка Vite (хэшированные чанки, CSS Modules вида `_Name_hash`), TanStack Query, zustand, Sentry. Берём React + TypeScript + Vite, CSS Modules, без UI-библиотеки. Данные через `fetch` к нашему HTTP API.
- **Шрифты:** Inter для текста (14px/20px, вес 400; подписи 12px), Inter Tight для заголовков (20px/28px, вес 600; display 24px/32px). Подключаем с Google Fonts.
- **Цвета (CSS-переменные Adapty, копируем в `tokens.css`):** текст `#111`, вторичный `#696969`; primary `#6720ff`, hover `#7e41ff`, мягкий фон `#f8f4ff`, нейтральный `#faf9fc`; рамки `#e7e7e7`, hover-фон `#f3f3f3`; статусы: зелёный `#1ea672` на `#f2faf5`, жёлтый `#eeae40` на `#faf7ed`, красный `#d74247` на `#fcedef`, синий `#4777ff` на `#f2f7ff`.
- **Геометрия:** сетка 4px, скругление кнопок 8px, пунктов меню 6px, карточки с рамкой 1px и скруглением 12px, контент 960px, левый сайдбар 240px белый с внутренней рамкой.
- **Паттерны со страницы теста Adapty:** хлебные крошки «← A/B tests / Имя теста», ряд иконок-действий (View in analytics, Duplicate, Modify, Stop), карточка статуса (Status · Live с зелёной точкой, Started at, Duration, Placement), таблица рук с чекбоксом цвета руки (B фиолетовый, A оранжевый) и пилюлей веса «50%», колонки P2BB и Predicted P2BB с текстом «insufficient data».

Поведение:

- Страница рендерит JSON ядра плюс конверт. Ползунок «As of day», поле «Traffic/day» и «Horizon» запрашивают `/verdict` с параметрами, ядро пересчитывает. Для живых тестов ползунка нет, есть только «Horizon» (1–120) и кнопка «Refresh».
- Данные читаются из кэша на диске. «Refresh» делает один живой проход (~5 вызовов CLI, 0,5 с между ними) и показывает время обновления. На демо кэш прогрет, «Refresh» нажимаем один раз на Onboarding.
- Кнопка «Stop» видна, но отключена, с подсказкой «Read-only prototype. Stop in Adapty after the verdict».
- Для живых тестов блок Segments показывает «Not available on live data», а не «0 checked».
- Тексты шаблонные, на английском, из полей JSON. Никакой генерации.

## 8. Контракт данных

**JSON ядра не меняем.** Он закрыт схемой `verdict_agent/schema.json` (`additionalProperties: false`), и любое поле это изменение через OpenSpec. Действующие поля: `ab_test_id`, `verdict`, `leader`, `p2bb_expected`, `p2bb_raw`, `horizon_days`, `horizon_source`, `maturity`, `come_back_on`, `money_at_stake_usd`, `arms[]` (`title`, `users`, `revenue_received`, `revenue_expected_trials`, `revenue_expected_renewals`, `warnings[]`), `segments_checked`, `segments_found[]`, `next_step` (`type`, `reason`, `placement_id`, `primary_metric`, `watch`, `alternative`), `source` (`live` | `offline`), `calibration_source` (`offline_calibration` в live, `offline` в offline). Выручка в `arms[]` на пользователя.

**HTTP-ответ** это конверт вокруг него:

```json
{
  "verdict": { "...": "JSON ядра без изменений" },
  "test": {
    "key": "995b124f-... | Settings: upgrade vs lifetime anchor",
    "name": "Onboarding: annual trial vs weekly first",
    "placement": {"id": "a0876118-...", "developer_id": "onboarding"},
    "status": "live | completed | offline",
    "started_on": "2026-11-07",
    "as_of": "2026-11-07",
    "arms": [{"title": "A", "flow_id": "fc4f9fe6-...", "weight": 0.5, "views": 254, "purchases": 0, "trials": 66}]
  },
  "checks": {
    "srm": {"status": "ok | broken", "chi2": 1.78, "p": 0.18},
    "dead_arm": {"status": "ok | broken"}
  },
  "after_stop": [{"audience": "All Users", "sees_now": ["A", "B"], "will_see": "B"}],
  "request": {"day": 14, "traffic": 100, "horizon": null},
  "refreshed_at": "2026-11-07T18:02:11Z"
}
```

Правило для `broken`: UI показывает красный бейдж «Test broken» поверх вердикта и прячет `next_step`. В JSON ядра `verdict` при этом остаётся как есть.

Что просим у Дмитрия в ядре, через OpenSpec, в порядке ценности для демо: разделить `tie` (п. 18); пороги `P_CONFIRM`, `MATURITY_MIN`, `MIN_EVENTS` как необязательные параметры `service.verdict()` по образцу `horizon`. Если не успевает, UI показывает пороги только для чтения, а ползунок меняет день, трафик и горизонт.

## 9. Агентная поверхность

- **MCP-тул `ab_test_verdict`** готов: параметры `ab_test_id` или `offline_test`, `day`, `traffic`, `horizon`. Регистрация через `.mcp.json.example`. Три записанных ответа Claude и их проверка лежат в `AI_LOG.md` и `eval/agent_runs/`.
- **`SKILL.md`** в формате adapty-skills: когда вызывать (перед `ab_tests_stop`, на вопросы «кто побеждает», «можно останавливать»), как объяснять (числа только из JSON, назвать live или offline), чего не делать (не останавливать тест, если вердикт не `confirmed`, и без явного «да» человека). Это показывает, как фича встраивается в экосистему `adapty-skills`.
